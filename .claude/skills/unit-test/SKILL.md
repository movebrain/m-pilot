# 단위 테스트 작성

> 이 저장소(mpilot) 전용 규칙이다. 단위 테스트를 우선하고, 통합 테스트는 구분 기준만 둔다. `docs/spec.md` 8.2의 테스트 규칙과 같이 움직인다.

## 도구와 실행

- 도구는 **pytest**다.
- `requirements.txt`는 서비스 이력 담당의 소유 파일이다(spec 8.1). pytest는 그 담당이 버전을 고정해 한 번만 추가하고, 이미 있으면 추가하지 않는다. 담당이 아니면 직접 고치지 않고 알린다.
- 실행은 저장소 루트에서 `python -m pytest`로 한다. 그냥 `pytest`는 `src`를 import하지 못해 실패한다.

```bash
python -m pytest
```

## 위치와 이름

- 테스트 파일은 `tests/test_<모듈>.py`다. 폴더 없이 평평하게 두고, 모듈 하나에 테스트 파일 하나다.

  | 소스 | 테스트 |
  | --- | --- |
  | `src/routing.py` | `tests/test_routing.py` |
  | `src/ui/customer.py` | `tests/test_customer.py` |

- 테스트 함수 이름은 `test_ac_<AC 번호>_<동작>`이다. AC 번호의 점은 밑줄로 바꾸고, 동작은 영어 `snake_case`로 쓴다(`python-naming` 스킬).
  - 예: AC-11.1 → `test_ac_11_1_high_severity_goes_to_support`
- AC 번호가 없는 테스트는 `test_<동작>`으로 쓴다.
- 테스트 하나는 동작 하나만 확인한다.

## 작성 순서: 테스트 먼저 (TDD)

1. AC와 테스트를 정한다. `intent-first`로 만든 `plan.md`의 **테스트** 절을 쓰고, `plan.md`가 없으면 `spec.md` 6.2의 해당 US AC나 사용자 설명을 쓴다.
2. AC마다 테스트를 먼저 쓰고 **실제로 실행해 실패하는 것을 확인한다**(red).
3. 통과하는 최소한의 구현을 쓴다(green).
4. 테스트를 통과한 채로 정리한다.

실패를 확인하지 않은 테스트는 아무것도 증명하지 못한다. 처음부터 통과하면 테스트가 잘못된 것이다.

## 외부 의존: LLM·벡터 DB는 가짜, db만 테스트 DB

**단위 테스트는 LLM API, 벡터 DB(Chroma), 네트워크에 접속하지 않는다.**

- `indexing`, `search`, `answer`, `history`는 `registry.py`의 `MPILOT_FAKES` 전환 장치와 고정 응답 JSON으로 가짜를 쓴다(`spec.md` 설계 규칙).
- 실제 구현은 불러올 때 외부에 접속하지 않으므로, 가짜로 전환하면 API 없이 돈다.
- 분기 판정(`route()`)처럼 외부에 의존하지 않는 순수 로직은 가짜 없이 입력과 기대 값만으로 검증한다.
- 가짜 구현이나 고정 응답이 아직 없으면 만들지 않고 질문한다. 형식은 담당 파트가 정한다.

**`db`(MySQL)는 가짜가 없어 직접 import하며, 테스트 DB를 쓴다.**

- 시연용 DB와 **분리된 테스트 DB**를 쓰고 테스트마다 비운다. 시연용 DB에는 접속하지 않는다.
- 접속 정보는 **환경 변수**(`.env.example`)로 받는다. 코드에 접속 정보를 넣지 않는다. 같은 테스트가 로컬 Docker MySQL과 GitHub Actions의 MySQL 서비스 컨테이너에서 모두 돌아야 한다.
- GitHub CI에는 API 키가 없다. 그러므로 `indexing`, `search`, `answer`, `history`는 항상 가짜로 돌고, 테스트가 실제 키를 요구하면 안 된다.
- CI 워크플로 파일은 첫 구현이 올라온 뒤에 추가한다. 지금은 위 규칙만 지킨다.

## LLM 출력 검증

단위 테스트는 **구조와 규칙만** 검증한다. 답의 정확도는 검증하지 않는다.

- 가짜 LLM 응답을 고정해 넣고 출력 검증 규칙을 단언한다. 예: 모든 단계에 인용이 1개 이상 있다, 형식이 맞다, "근거 부족"과 "적용 대상 아님"이면 조치 단계가 비어 있다.
- 답이 맞는지는 `evaluate.py`의 평가가 맡는다.
- 실제 LLM API를 호출하지 않는다.

## 무엇을 테스트할까

필요한 것만 고른다. 다음 중 해당하는 것이 있으면 빠뜨리지 않는다.

- **경계값과 실패 경로**: 24시간 5회 경계, 설비-에러코드 쌍 0개·5개·중복 거부, 빈 입력
- **표 데이터**: 입력 → 기대 결과가 표로 나오는 규칙은 `@pytest.mark.parametrize`로 한 함수에 여러 행으로 쓴다.
- **도메인 불변식**: 설비 필터를 걸면 다른 설비 문서가 나오지 않는다, 모든 단계에 인용이 있다, 근거 부족과 적용 대상 아님을 구분한다
- **상태 전이와 중복 방지**: 허용되지 않는 전이는 에러가 난다, 접수번호가 겹치지 않는다(테스트 DB 필요), 이미 있는 요약은 다시 만들지 않는다

Gradio 화면에서만 확인되는 AC(렌더링·문구·배치)는 pytest로 쓰지 않고 `spec.md` 8.2의 수동 체크리스트로 점검한다. 핸들러가 부르는 함수 호출 순서와 저장값은 pytest로 쓴다.

## 단위와 통합의 구분

| | 단위 | 통합 |
| --- | --- | --- |
| 외부 접속 | LLM·벡터 DB·네트워크 없음(가짜), db는 테스트 DB | 실제 구현을 이어 6.4 시나리오를 끝까지 실행 |
| 위치 | `tests/test_<모듈>.py` | `tests/test_integration.py` (서비스 이력 담당) |
| 실행 | 항상 실행, CI에서도 실행 | 환경이 필요해 필요할 때 실행 |

- 통합 테스트 작성 방법은 이 스킬이 다루지 않는다. 필요하면 요청한다.

## 완료 기준

테스트 작업이 끝났다고 말하기 전에 다음을 모두 한다.

1. 대상 AC가 모두 테스트 이름에 매핑되어 있는지 확인한다. 수동 체크리스트로 점검하기로 한 AC는 제외한다.

   ```bash
   grep -rhoE "test_ac_[0-9_]+" tests | sort -u
   ```

2. **`python -m pytest`를 실제로 실행**하고 통과 결과를 보고한다. 통과 수와 실행 시간을 함께 쓴다.
3. 실패하거나 건너뛴 테스트가 있으면 숨기지 않고 이유와 함께 보고한다.

커버리지 수치 목표는 두지 않는다. AC 매핑과 통과 출력이 기준이다.

## 의도 확인 (가이드 질문)

아래 상황에서 판단이 서지 않으면 추측하지 않고 `AskUserQuestion`으로 묻는다. 분명하면 묻지 않는다.

- **단위와 통합의 경계가 불분명할 때**: 여러 모듈을 거치지만 모두 가짜인 테스트처럼 애매하면 어느 쪽에 둘지 확인한다.
- **AC 번호가 없을 때**: 테스트할 동작에 해당하는 AC가 없으면 spec에 AC를 추가할지 확인한다.
- **가짜 구현이나 고정 응답이 없을 때**: 형식을 어떻게 할지, 누가 만들지 확인한다.
- **LLM 호출만 가짜로 바꿀 방법이 없을 때**: 모듈 내부(인용 검증 등)를 테스트하는데 `registry`로는 모듈 전체만 바뀌면, LLM 호출 부분을 바꾸는 방법을 구현에서 어떻게 둘지 확인한다.
- **테스트하기 어려운 구조일 때**: 외부 접속이 함수 안에 박혀 있어 가짜로 바꿀 수 없으면 구현을 고칠지 확인한다.

## 하지 말 것

- 단위 테스트에서 실제 LLM API, 벡터 DB, 네트워크 접속
- 시연용 DB에 접속하는 테스트, 접속 정보를 코드에 넣기
- 구현을 먼저 쓰고 테스트를 거기에 맞추기
- 실패를 확인하지 않은 테스트
- 통과시키려고 단언을 약하게 바꾸기
- 실패하는 테스트를 `skip`, `xfail`로 숨기기
- 단위 테스트에서 LLM 답의 정확도 단언
- `sleep`에 의존하는 테스트, 실행 순서에 의존하는 테스트
- `requirements.txt`를 담당이 아닌 파트가 직접 수정
- `python -m pytest`를 실행하지 않고 "통과한다"고 보고
