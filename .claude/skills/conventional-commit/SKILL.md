# 커밋 컨벤션 (Conventional Commits 1.0.0)

> 이 저장소(mpilot) 전용 규칙이다. 다른 저장소나 개인용 커밋 스킬과 섞어 쓰지 않는다.
> `origin/develop`의 `.github/CONTRIBUTING.md`(`타입: 설명`, type 6개)보다 이 스킬이 우선한다 (`branch-strategy`의 "정본" 참조). `feat: 제목`처럼 scope 없는 형식도 이 스킬에서 유효하다.

명세: https://www.conventionalcommits.org/en/v1.0.0/

## 메시지 구조

```
<type>[(scope)][!]: <한국어 제목>

<본문: 무엇을 바꿨는지 + 왜 바꿨는지(의도)>

[footer]
```

- 제목과 본문 사이, 본문과 footer 사이는 빈 줄 한 줄로 구분한다.
- **접두사(`type`, `scope`)만 영어**, 그 외 제목·본문·footer 설명은 모두 **한국어**로 쓴다.
  - 고유명사·코드 식별자·파일 경로·에러코드는 원문 그대로 둔다 (예: `AGV`, `docs/spec.md`).
- **Claude 관련 `Co-authored-by` 트레일러와 "Generated with Claude Code" 문구는 절대 넣지 않는다.** 이 규칙은 다른 기본 동작보다 우선한다.

## type

| type | 용도 | SemVer |
| --- | --- | --- |
| `feat` | 새 기능 추가 | MINOR |
| `fix` | 버그 수정 | PATCH |
| `docs` | 문서만 변경 | - |
| `style` | 동작에 영향 없는 서식 변경 (공백, 세미콜론 등) | - |
| `refactor` | 동작 변경 없는 구조 개선 | - |
| `perf` | 성능 개선 | - |
| `test` | 테스트 추가·수정 | - |
| `build` | 빌드 시스템·의존성 변경 | - |
| `ci` | CI 설정 변경 | - |
| `chore` | 위에 속하지 않는 잡무 | - |

- 변경이 여러 종류에 걸치면 커밋을 나누는 것을 우선 검토한다. 나눌 수 없을 때는 가장 영향이 큰 type 하나를 고른다.
- `scope`는 변경 영역을 나타내는 명사를 괄호로 감싼다. 예: `feat(parser):`, `docs(spec):`. 의미 있는 영역이 없으면 생략한다.

## 제목

- `type(scope):` 접두사를 포함해 **50자 이내**의 한 줄, 마침표 없이 끝낸다.
- 무엇을 했는지 명사형 또는 간결한 서술형으로 쓴다. 예: `저위험 건 분기 규칙 추가`, `매뉴얼 검색 설비 필터 누락 수정`.
- 모호한 표현(`수정`, `업데이트`, `작업`만 단독 사용)을 피한다.

## 본문 (필수)

- 본문은 **의도**를 반드시 포함한다. 코드를 보면 알 수 있는 "무엇"보다 **"왜 이렇게 바꿨는가"** 를 중심으로 쓴다.
  - 어떤 문제·요구가 있었는가
  - 왜 이 방식을 택했는가 (대안이 있었다면 왜 배제했는가)
  - 이 변경으로 기대하는 결과
- 여러 항목은 불릿(`-`)으로 나열해도 좋다. 한 줄은 72자 안팎에서 줄바꿈한다.
- 사소한 변경이라도 한 줄 이상 의도를 남긴다.
- 의도를 diff나 대화에서 알 수 없으면 추측으로 채우지 말고 아래 가이드 질문으로 확인한다.

## 의도 확인 (가이드 질문)

변경의 **의도(왜)** 가 diff, 대화 맥락, 기존 커밋·문서에서 분명하면 묻지 않고 바로 작성한다. **불분명할 때만** `AskUserQuestion`으로 묻는다.

- 한 번에 1~3개만 묻는다. 이미 아는 내용은 묻지 않는다.
- 사용자가 고르기 쉽도록 추측 가능한 답을 선택지로 제시하고, 직접 입력(Other)도 받는다.
- 질문 후보 (상황에 맞는 것만 고른다):
  - 이 변경은 어떤 문제나 요구에서 시작됐나요?
  - 이 방식을 택한 이유는 무엇인가요? 검토했다가 배제한 대안이 있나요?
  - 이 변경으로 기대하는 결과, 또는 달라지는 동작은 무엇인가요?
  - 기존 사용자·호출부에 영향(호환성 깨짐)이 있나요?
  - 연결할 이슈가 있나요?
- 답변은 사용자의 말을 살려 본문에 한국어로 정리한다.

## footer

- 호환성을 깨는 변경: 제목의 type/scope 뒤에 `!`를 붙이고, footer에 `BREAKING CHANGE: <영향과 대응 방법>`을 쓴다. 토큰 `BREAKING CHANGE`는 대문자·영어 그대로 쓴다.
- 이슈 연결: `Refs #123`, `Closes #123` (콜론 없이. `create-pr`의 이슈 링크와 같은 표기).
- Claude `Co-authored-by` 는 쓰지 않는다. 사람 공동 작성자가 있어 사용자가 명시한 경우에만 해당 사람의 트레일러를 넣는다.

## 절차

0. 현재 브랜치가 `main`이나 `develop`이면 커밋하지 않고 `branch-strategy` 스킬에 따라 `<type>/<설명>` 작업 브랜치를 먼저 만든다. 작업 트리가 더러워 `develop`으로 전환할 수 없으면 그 스킬대로 멈추고 묻는다.
1. `git status`, `git diff --staged`(스테이징된 게 없으면 `git diff`)로 변경 내용을 파악한다. 최근 `git log --oneline -10`으로 기존 스타일도 확인한다.
2. 스테이징할 파일이 정해져 있지 않으면 논리적 단위로 묶어 필요한 파일만 `git add <경로>` 한다. `git add -A`는 의도치 않은 파일이 섞일 수 있으니 피한다.
3. 변경 의도가 분명한지 점검하고, 불분명하면 위 **가이드 질문**으로 확인한다.
4. type, scope, 제목, 의도가 담긴 본문을 작성한다.
5. HEREDOC으로 커밋한다.

   ```bash
   git commit -F - <<'EOF'
   docs(spec): 반복 에러 집계에 이번 건 포함 명시

   - 5회 기준이 '이번 건 포함'인지 모호하면 4회째·5회째 경계에서
     분기 결과가 구현마다 달라질 수 있었음
   - AC-04.3과 AC-11.2에 같은 기준을 적어 경계 시각 테스트가
     하나의 해석만 확인하게 하려는 목적
   EOF
   ```

6. 커밋 후 `git log -1 --format=%B`로 확인하여 Co-authored-by 가 없고 형식이 맞는지 점검한다.

## 예시

M-Pilot(`docs/intent.md`, `docs/spec.md`)의 내용을 바탕으로 한 **형식 설명용 예시**다. 실제 커밋 이력이 아니다.

```
feat(routing): 심각도 상 고객사 조치 코드를 기술지원 건으로 분기

- 비상정지(M440), 안전 펜스 도어 개방(M441)처럼 조치 구분이
  `고객사 조치`여도 심각도 `상`인 코드는 고객이 직접 조치하면 위험함
- 안내 문구를 쓰는 사람의 판단이 아니라 표의 severity 값만으로
  막아, 안전 기준이 사람에 따라 달라지지 않게 하려는 목적
```

```
fix(search): 매뉴얼 검색에 설비 필터 누락 수정

- SRM S112와 RTV R201은 모두 주행 인버터 과전류라 설비 필터 없이
  의미 검색하면 서로 섞여 나옴
- 다른 설비의 조치를 안내하면 현장에서 잘못된 절차를 따를 수 있어
  retrieve의 모든 검색에 equipment 필터를 적용
```

```
refactor(data)!: 에러코드 표기를 설비 접두 체계로 통일

- 사양서 PDF는 `E401`, 대응표 CSV는 `M401`로 표기가 갈려 같은
  코드를 두 가지 방식으로 조회해야 했음
- `code`를 설비 접두 체계 하나로 통일해 조회 기준을 하나로
  만들기 위함

BREAKING CHANGE: `code` 값이 `E401`에서 `M401` 형식으로 바뀌므로
기존 이력의 `error_code`도 같은 기준으로 변환해야 한다.
```

## 하지 말 것

- `Co-authored-by: Claude ...` 또는 `🤖 Generated with Claude Code` 추가
- 제목·본문을 영어로 작성 (접두사 제외)
- 의도 없이 변경 목록만 나열하는 본문
- 의도를 모르는데 그럴듯하게 지어내서 채우기 (모르면 질문한다)
- 서로 무관한 변경을 하나의 커밋에 묶기
