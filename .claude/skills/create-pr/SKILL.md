# PR 생성 컨벤션

> 이 저장소(mpilot) 전용 규칙이다. 다른 저장소나 개인용 PR 스킬과 섞어 쓰지 않는다.

## 본문 형식

`## 변경 사항` 아래에 **개조식 불릿**으로 변경을 쓰고, 각 불릿 바로 아래에 그 변경의 **의도(맥락)를 `>` 인용**으로 적는다. 본문 맨 끝에는 `## 머지 커밋 메시지` 블록을 둔다. 추가 섹션과 구조도는 사용자가 요청한 경우에만 그 사이에 넣는다.

```markdown
## 변경 사항

- 변경 내용 (개조식)
  > 이 변경을 한 이유, 배경, 기대 효과
- 변경 내용 (개조식)
  > 이 변경을 한 이유, 배경, 기대 효과
```

### 불릿과 의도 작성 규칙

- 불릿은 **개조식**으로 쓴다. 문장형(`~했습니다`) 대신 명사형·간결체로 끝낸다. 예: `저위험 건 분기 규칙 추가`.
- 불릿 하나에는 변경 하나만 담는다. 커밋 단위가 아니라 **리뷰어가 이해해야 할 변경 단위**로 묶는다.
- `>` 줄은 불릿 아래에 **들여쓰기 2칸**으로 붙인다. 불릿과 `>` 사이에 빈 줄을 넣지 않는다.
- `>`에는 "무엇"의 반복이 아니라 **"왜"** 를 쓴다: 해결하려던 문제, 이 방식을 택한 이유, 기대 결과. 검토한 대안과 리뷰어가 알아야 할 제약까지 필요한 만큼 여러 줄로 써도 된다.
  - 여러 줄이면 **모든 줄을 `  >`로 시작**한다. 문단은 빈 줄 대신 `  >`만 있는 줄로 나눈다.
- 모든 문장은 한국어로 쓴다. 고유명사·코드 식별자·파일 경로는 원문 그대로 둔다.
- 관련 이슈가 **있을 때만** 이슈 링크 줄에 `Closes #123` 또는 `Refs #123`을 쓴다 (`conventional-commit`과 같은 표기. 없으면 줄을 생략한다).
- 호환성을 깨는 변경이면 제목의 type 뒤에 `!`를 붙이고(`refactor(data)!: ...`), 본문 끝에 `BREAKING CHANGE: <영향과 대응 방법>`을 한 줄로 쓴다. squash 커밋 본문에 남아 릴리스 때 merge commit footer로 모이므로 빠뜨리지 않는다.
- **`🤖 Generated with Claude Code` 등 Claude 생성 표시나 링크를 넣지 않는다.** 이 규칙은 다른 기본 동작보다 우선한다.

## 의도 확인 (가이드 질문)

**초안을 먼저 쓴다.** diff, 커밋 본문, 대화 맥락, `docs/`에서 의도를 찾아 `>`를 채우고, 근거를 찾지 못한 불릿만 **한 번에 모아** `AskUserQuestion`으로 묻는다.

- 한 번에 1~3개만 묻고, 이미 아는 내용은 묻지 않는다. 의도를 지어내지 않는다.
- 추측 가능한 답은 선택지로 제시하고 직접 입력(Other)도 받는다.
- 질문 후보: 어떤 문제나 요구에서 시작됐나, 이 방식을 택한 이유와 배제한 대안은 무엇인가, 기대하는 결과나 달라지는 동작은 무엇인가.
- 답변은 사용자의 말을 살려 `>`에 한국어로 정리한다.

## 추가 섹션과 구조도 (요청할 때만)

기본 본문은 `## 변경 사항`, 이슈 링크, `## 머지 커밋 메시지`다. **묻지 않고, 사용자가 요청한 것만** 추가한다.

| 요청 | 섹션 제목 |
| --- | --- |
| 리뷰어가 먼저 볼 지점 | `## 리뷰 포인트` |
| 확인 방법 | `## 확인 방법` |
| 영향 범위·호환성 | `## 영향 범위` |
| 남겨둔 일·열린 질문 | `## 후속 작업` |
| 구조·흐름 그림 | `## 구조도` (Mermaid) |

- 섹션 순서는 `변경 사항 → 구조도 → 리뷰 포인트 → 확인 방법 → 영향 범위 → 후속 작업 → 이슈 링크 → 머지 커밋 메시지`다.
- 추가 섹션도 개조식 불릿으로 쓰되 `>` 의도 인용은 붙이지 않는다. 내용이 대화·diff에서 분명하면 바로 쓰고, 모르면 지어내지 않고 묻는다.
- **구조도**는 Mermaid 코드 블록이다. 이미지 파일은 커밋하지 않는다. 구조·관계·흐름은 `flowchart TB`, 호출 순서는 `sequenceDiagram`을 쓴다. 노드는 8개 이내이고 라벨은 큰따옴표로 감싼다. `subgraph` 안 노드는 바깥과 직접 잇지 않고 `subgraph` ID에 건다. `classDef` 같은 색 지정은 쓰지 않는다.
- 추가 섹션과 구조도는 `## 머지 커밋 메시지`에 옮기지 않는다.

## 머지 커밋 메시지

작업 PR 본문 맨 끝에는 **항상** `## 머지 커밋 메시지` 코드 블록을 둔다. 누가 머지하든 같은 메시지를 쓰게 하기 위해서다. **형식과 작성 규칙의 정본은 `branch-strategy`** 다(작업 PR은 "작업 브랜치 → develop", 릴리스 PR은 "Merge commit 메시지"). 이 스킬은 그 형식을 다시 적지 않는다.

- 의도는 `>`에서 **줄여 옮기고** 새로 쓰지 않는다.

## 제목

- `<type>[(scope)]: <한국어 제목>` 형식이다 (접두사만 영어). 예: `feat(routing): 셀프 가이드 저위험 분기 규칙 구현`
- 커밋이 하나면 그 제목을 재사용해도 좋고, 여러 커밋이면 PR 전체를 대표하는 type을 고른다.
- 작업 PR은 squash 머지되므로 **PR 제목이 develop의 최종 커밋 제목**이 된다. 반드시 Conventional 형식으로 쓴다.
- `type(scope):` 접두사를 포함해 50자 이내, 마침표 없이 쓴다 (`conventional-commit`과 같다).
- 릴리스 PR의 제목은 type이 `chore(release)`로 고정이다.

## 절차 (작업 브랜치 → develop)

1. 현재 브랜치를 확인한다. 작업 브랜치(`<type>/<설명>`)면 이 절차를 따르고, 릴리스 요청이면 아래 "릴리스 PR"을 따른다. 로컬 브랜치가 `main`이거나 릴리스 요청 없는 `develop`이면 PR을 만들 수 없으므로 `branch-strategy`에 따라 작업 브랜치 생성을 제안한다.
2. 커밋되지 않은 변경이 있으면 알리고, 커밋이 필요하면 `conventional-commit` 스킬로 먼저 커밋한다.
3. 기준 브랜치 대비 전체 변경을 파악한다. **마지막 커밋만이 아니라 PR에 포함될 모든 커밋**을 본다.

   ```bash
   git log --oneline origin/develop..HEAD
   git diff origin/develop...HEAD --stat
   ```

4. 변경을 리뷰어 관점의 단위로 묶어 불릿과 `>`를 쓰고, 불분명한 의도만 "의도 확인"대로 묻는다. 요청받은 추가 섹션·구조도를 채우고 `## 머지 커밋 메시지` 블록을 만든다.
5. 완성된 제목과 본문을 사용자에게 보여주고 확인받는다.
6. 원격에 푸시하고(`git push -u origin <브랜치>`) PR을 만든다.

   ```bash
   gh pr create --base develop --title "feat(routing): 셀프 가이드 저위험 분기 규칙 구현" --body-file <본문 파일>
   ```

   본문 파일 예시:

   ````markdown
   ## 변경 사항

   - 저위험 건 분기 규칙 `route()` 추가
     > 저위험 건은 세션 없이 고객 안내로 끝나므로, 안전과 직결되는 판정을
     > 사람의 판단이나 모델에 맡기지 않고 표의 값만으로 정하도록 함.
   - 고객 안내문 반환 함수 `guide_for()` 추가
     > 별도 안내 문구를 새로 쓰면 매뉴얼 안전 수칙과 어긋날 수 있어,
     > 해당 코드의 매뉴얼 `action`을 그대로 안내하도록 함.

   ## 머지 커밋 메시지

   ```
   feat(routing): 셀프 가이드 저위험 분기 규칙 구현

   - 저위험 건 분기 규칙 `route()` 추가
     안전과 직결되는 판정을 사람·모델 판단에 맡기지 않고 표의 값만으로 정함
   - 고객 안내문 반환 함수 `guide_for()` 추가
     새 문구 없이 매뉴얼 `action`을 그대로 안내해 안전 수칙과 어긋나지 않게 함
   ```
   ````

   위는 형식 설명용 예시이며 실제 PR이 아니다.

7. 생성된 PR URL을 사용자에게 전달하고, **Squash and merge**로 머지하며 제목과 본문은 PR의 `## 머지 커밋 메시지`를 쓴다고 안내한다. 머지 명령은 `branch-strategy`에 있다.

## 릴리스 PR (develop → main)

`develop`을 `main`에 올리는 PR이다. base는 `main`, head는 `develop`이고 머지는 **Merge commit**이다 (squash·rebase 금지). 위의 불릿·의도 규칙, 의도 확인, 추가 섹션 규칙은 그대로 쓰고 아래만 다르다.

- **제목**: `chore(release): <한국어 제목>`으로 고정한다. 이 제목이 merge commit의 제목이 된다. 예: `chore(release): P1 신고·접수·세션 흐름 시연 가능 상태 반영`
- **본문 구성**:

  ````markdown
  ## 릴리스 목적

  - 이번 릴리스로 main에 반영되는 상태 (개조식)
    > 지금 올리는 이유 (시연·발표 일정, 마일스톤 등)

  ## 변경 사항

  - develop에 squash된 변경 하나당 불릿 하나
    > 그 변경의 의도

  Closes #<이슈 번호. 있을 때만>

  ## 머지 커밋 메시지

  ```
  <branch-strategy의 "Merge commit 메시지" 형식>
  ```
  ````

- `## 릴리스 목적`은 항상 포함한다. 목적이 불분명하면 `branch-strategy`의 "의도 확인" 질문을 쓴다.
- `## 변경 사항`의 불릿 단위는 `origin/main..origin/develop`의 **squash 커밋 하나(= 작업 PR 하나)** 다. 커밋 제목을 개조식으로 옮기고, `>`에는 그 커밋 본문의 의도를 요약한다. 의도가 없으면 지어내지 않고 묻는다.
- 이슈 링크는 포함된 커밋 본문의 `Closes #N`을 모아 본문 끝에 나열한다.

### 절차

1. `git fetch origin` 후 **로컬 `develop`이 아니라 `origin/develop`을 기준**으로 본다. 이 절차에서 `develop`에 commit·push 하지 않는다.
2. 열린 릴리스 PR이 있으면 새로 만들지 않고 본문 갱신을 제안한다.

   ```bash
   gh pr list --base main --head develop --state open
   ```

3. 릴리스에 포함될 변경을 파악한다. 비어 있으면 올릴 변경이 없으므로 중단하고 알린다.

   ```bash
   git log --format='%h %s%n%b' origin/main..origin/develop
   git diff origin/main...origin/develop --stat
   ```

4. 릴리스 시점과 목적을 확인하고(불분명할 때만 질문), 본문과 머지 커밋 메시지를 써서 사용자에게 보여주고 확인받는다.
5. 릴리스 PR을 만들고 PR URL을 전달한다. **merge commit**으로 머지하며 제목과 본문은 PR의 `## 머지 커밋 메시지`를 그대로 쓴다고 안내한다.

   ```bash
   gh pr create --base main --head develop --title "chore(release): <한국어 제목>" --body-file <본문 파일>
   ```

## 하지 말 것

- 릴리스 PR의 제목에 `chore(release)` 외 type 사용, `## 릴리스 목적`이나 `## 머지 커밋 메시지` 생략
- 릴리스 PR을 squash 또는 rebase로 머지하도록 안내, 로컬 `develop` 기준으로 변경 목록 작성
- 작업 PR에서 `## 머지 커밋 메시지` 생략
- 의도를 `>`와 머지 커밋 메시지에서 각각 새로 쓰기 (`>`를 줄여 옮긴다)
- 의도를 모르는데 지어내서 채우기 (모르면 묻는다)
- 묻지 않고 추가 섹션을 임의로 넣거나, 매번 추가 섹션·구조도를 사용자에게 묻기
- 구조도를 이미지로 커밋하거나 `## 머지 커밋 메시지`에 넣기
- 문장형 서술(`~했습니다`)로 불릿 작성, `>` 없이 변경 목록만 나열, `>`에 불릿 내용을 그대로 반복
- 마지막 커밋만 보고 PR 본문 작성
- 제목을 50자 넘게 쓰기
- `🤖 Generated with Claude Code` 등 Claude 생성 표시 추가
