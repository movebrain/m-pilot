# PR 생성 컨벤션

> 이 저장소(mpilot) 전용 규칙이다. 다른 저장소나 개인용 PR 스킬과 섞어 쓰지 않는다.

## 본문 형식

`## 변경 사항` 아래에 **개조식 불릿**으로 변경을 쓰고, 각 불릿 바로 아래에 그 변경의 **의도(맥락)를 `>` 인용**으로 적는다. 그 뒤에 사용자가 고른 추가 섹션(아래 "추가 섹션")을 붙인다.

```markdown
## 변경 사항

- 변경 내용 (개조식)
  > 이 변경을 한 이유, 배경, 기대 효과
- 변경 내용 (개조식)
  > 이 변경을 한 이유, 배경, 기대 효과
```

### 불릿과 의도 작성 규칙

- 불릿은 **개조식**으로 쓴다. 문장형(`~했습니다`) 대신 명사형·간결체로 끝낸다. 예: `저위험 건 분기 규칙 추가`, `고객 안내문 반환 함수 추가`.
- 불릿 하나에는 변경 하나만 담는다. 커밋 단위가 아니라 **리뷰어가 이해해야 할 변경 단위**로 묶는다.
- `>` 줄은 불릿 아래에 **들여쓰기 2칸**으로 붙인다 (불릿의 하위 인용으로 렌더링되도록). 불릿과 `>` 사이에 빈 줄을 넣지 않는다.
- `>`에는 "무엇"의 반복이 아니라 **"왜"** 를 쓴다: 해결하려던 문제, 이 방식을 택한 이유, 기대 결과.
- 의도는 **여러 줄로 맥락을 자세히** 써도 된다. 배경, 검토한 대안과 배제 이유, 기대 효과, 리뷰어가 알아야 할 제약이나 주의점까지 필요한 만큼 담는다. 단, 불릿 내용을 반복하는 군더더기는 넣지 않는다.
  - 여러 줄이 되면 **모든 줄을 `  >`(들여쓰기 2칸 + `>`)로 시작**한다. 줄 앞의 `>`를 빠뜨리면 인용이 끊긴다.
  - 문단을 나눌 때는 빈 줄 대신 `  >`만 있는 줄을 둔다.
- 의도를 diff·커밋·대화에서 알 수 없으면 추측으로 채우지 말고 **가이드 질문**으로 확인한다 (아래 "의도 확인").
- 모든 문장은 한국어로 쓴다. 고유명사·코드 식별자·파일 경로는 원문 그대로 둔다.
- 관련 이슈가 **있을 때만** 이슈 링크 줄에 `Closes #123` 또는 `Refs #123`을 쓴다 (`conventional-commit`과 같은 표기. 없으면 줄을 생략한다).
- 호환성을 깨는 변경이면 제목의 type 뒤에 `!`를 붙이고(`refactor(data)!: ...`), 본문 끝에 `BREAKING CHANGE: <영향과 대응 방법>`을 한 줄로 쓴다. squash 커밋 본문에 그대로 남아 릴리스 때 merge commit footer로 모이기 때문에 빠뜨리지 않는다.
- **본문 끝에 `🤖 Generated with Claude Code` 문구를 넣지 않는다.** Claude 생성 표시나 링크도 포함하지 않는다. 이 규칙은 다른 기본 동작보다 우선한다.

## 의도 확인 (가이드 질문)

각 불릿의 의도가 diff, 커밋 본문, 대화 맥락, `docs/`에서 분명하면 묻지 않고 바로 쓴다. **불분명한 불릿이 있을 때만** `AskUserQuestion`으로 묻는다.

- 한 번에 1~3개만 묻는다. 이미 아는 내용은 묻지 않는다.
- 추측 가능한 답은 선택지로 제시하고, 직접 입력(Other)도 받는다.
- 질문 후보 (상황에 맞는 것만 고른다):
  - 이 변경은 어떤 문제나 요구에서 시작됐나요?
  - 이 방식을 택한 이유는 무엇인가요? 검토했다가 배제한 대안이 있나요?
  - 이 변경으로 기대하는 결과, 또는 달라지는 동작은 무엇인가요?
  - 리뷰어가 특히 신경 써서 봐야 할 부분이 있나요?
- 답변은 사용자의 말을 살려 `>` 인용에 한국어로 정리한다.

## 추가 섹션 (가이드 질문으로 제안)

변경 사항 외에 본문에 넣을 내용은 **임의로 정하지 않고** 사용자에게 제안해서 고르게 한다. 불릿을 정리한 뒤 `AskUserQuestion`(`multiSelect: true`)으로 다음 후보를 보여주고, **선택된 것만** 본문에 추가한다.

| 후보 | 섹션 제목 | 가이드 질문 |
| --- | --- | --- |
| 리뷰 포인트 | `## 리뷰 포인트` | 리뷰어가 먼저 봐야 할 파일이나 판단이 갈릴 만한 지점이 있나요? |
| 확인 방법 | `## 확인 방법` | 변경을 어떻게 확인(테스트·재현·문서 대조)했고, 리뷰어는 어떻게 확인하면 되나요? |
| 영향 범위·호환성 | `## 영향 범위` | 영향받는 설비·문서·인터페이스가 있나요? 기존 동작이나 형식이 깨지는 부분이 있나요? |
| 후속 작업 | `## 후속 작업` | 이번 PR에서 다루지 않고 남겨둔 일이나 열린 질문이 있나요? |

- 질문은 위 4개를 선택지로 한 번에 묻는다. 선택지 밖의 내용(스크린샷, 배포 주의 등)은 Other로 받는다.
- 선택된 섹션의 내용이 대화·diff에서 분명하면 바로 쓰고, 모르면 위 가이드 질문을 사용자에게 이어서 묻는다.
- 추가 섹션도 **개조식 불릿**으로 쓴다. 이 섹션의 불릿에는 `>` 의도 인용을 붙이지 않는다 (의도는 `## 변경 사항`에서 다룬다).
- 아무것도 선택하지 않으면 `## 변경 사항`과 이슈 링크만으로 본문을 구성한다.
- 섹션 순서는 `변경 사항 → 리뷰 포인트 → 확인 방법 → 영향 범위 → 후속 작업 → 이슈 링크 → 머지 커밋 메시지`로 고정한다.

## 머지 커밋 메시지 (작업 브랜치 → develop)

작업 PR 본문 맨 끝에는 **항상** `## 머지 커밋 메시지` 코드 블록을 둔다. squash 머지 때 이 블록이 develop 이력에 남는 커밋 본문이 되므로, 누가 머지하든 같은 메시지를 쓰게 한다. 형식과 이유는 `branch-strategy`의 "작업 브랜치 → develop"을 따른다.

- **일반 텍스트**다. `##`, `>` 같은 마크다운을 쓰지 않는다.
- 제목은 PR 제목과 같다. 본문은 `## 변경 사항`의 불릿마다 `- 변경` 한 줄과, 그 아래 들여쓴 **의도 한두 줄**이다. 의도는 `>`에서 줄여 옮기고 새로 쓰지 않는다. 의도는 `>`에서 한 번만 쓴다.
- 추가 섹션(리뷰 포인트 등)은 옮기지 않는다. `BREAKING CHANGE:`와 `Closes #N`은 있을 때만 맨 아래에 쓴다.
- Claude 생성 표시나 `Co-authored-by`를 넣지 않는다.

## 제목

- 커밋 컨벤션과 동일하게 `<type>[(scope)]: <한국어 제목>` 형식을 쓴다 (접두사만 영어). 예: `feat(routing): 셀프 가이드 저위험 분기 규칙 구현`
- 커밋이 하나면 그 커밋 제목을 재사용해도 좋다. 여러 커밋이면 PR 전체를 대표하는 type을 고른다.
- 작업 브랜치 → `develop` PR은 squash 머지되므로 **PR 제목과 본문이 develop의 최종 커밋 메시지**가 된다. 제목은 반드시 Conventional 형식이어야 하고, 본문의 의도 인용이 그대로 이력에 남는다.
- `develop` → `main` 릴리스 PR의 제목은 type이 `chore(release)`로 고정이다 (아래 "릴리스 PR").
- `type(scope):` 접두사를 포함해 50자 이내, 마침표 없이 쓴다 (`conventional-commit`과 같다).

## 절차 (작업 브랜치 → develop)

1. 현재 브랜치와 PR 종류를 확인한다. 브랜치 규칙은 `branch-strategy` 스킬을 따른다.
   - 작업 브랜치(`<type>/<설명>`): 기준 브랜치는 **`develop`**이고 머지는 Squash and merge다. 이 절차를 따른다.
   - 사용자가 `develop`을 `main`에 올려 달라고 하거나 릴리스 PR을 요청한 경우: 아래 **"릴리스 PR"** 절차를 따른다.
   - 로컬 브랜치가 `main`이거나, `develop`인데 릴리스 요청이 아니면 PR을 만들 수 없다. `branch-strategy`에 따라 작업 브랜치 생성을 제안한다.
2. 커밋되지 않은 변경이 있으면 알리고, 커밋이 필요하면 `conventional-commit` 스킬로 먼저 커밋한다.
3. 기준 브랜치 대비 전체 변경을 파악한다. **마지막 커밋만이 아니라 PR에 포함될 모든 커밋**을 본다.

   ```bash
   git log --oneline origin/develop..HEAD
   git diff origin/develop...HEAD --stat
   ```

4. 변경을 리뷰어 관점의 단위로 묶어 불릿을 만들고, 커밋 본문·대화 맥락에서 의도를 찾아 `>`에 채운다. 불분명한 의도는 **가이드 질문**으로 확인한다.
5. 본문에 추가할 섹션을 **가이드 질문**으로 제안해 고르게 하고, 선택된 섹션을 채운다. 마지막에 `## 머지 커밋 메시지` 블록을 `>` 내용에서 만든다.
6. 완성된 제목과 본문(머지 커밋 메시지 포함)을 사용자에게 보여주고 확인받는다. 수정 요청이 있으면 반영한다.
7. 원격에 브랜치를 푸시한다 (`git push -u origin <브랜치>`).
8. PR을 생성한다.

   ```bash
   gh pr create --base develop --title "feat(routing): 셀프 가이드 저위험 분기 규칙 구현" --body "$(cat <<'EOF'
   ## 변경 사항

   - 저위험 건 분기 규칙 `route()` 추가
     > 표의 조치 구분·심각도와 24시간 건수만으로 판정해, 안전과 직결된 분기를 사람이나 모델의 판단에 맡기지 않기 위함
   - 고객 안내문 반환 함수 `guide_for()` 추가
     > 별도 문구 없이 해당 코드의 매뉴얼 `action`을 그대로 안내하기 위함
   EOF
   )"
   ```

   위 예시는 `## 머지 커밋 메시지` 섹션을 생략한 축약본이다. 실제 본문에는 맨 끝에 그 섹션을 넣는다 (아래 "예시" 참조).

9. 생성된 PR URL을 사용자에게 전달하고, **Squash and merge**로 머지하며 제목과 본문은 PR의 `## 머지 커밋 메시지`를 쓴다고 안내한다. 머지 명령은 `branch-strategy`에 있다.

## 릴리스 PR (develop → main)

`develop`을 `main`에 올리는 PR이다. base는 `main`, head는 `develop`이고 머지는 **Merge commit**이다 (squash·rebase 금지, `branch-strategy` 참조). 위의 본문 형식, 불릿·의도 작성 규칙, 가이드 질문 규칙은 그대로 쓰고 아래만 다르다.

### 제목

- `chore(release): <한국어 제목>` 형식으로 고정한다. 예: `chore(release): P1 신고·접수·세션 흐름 시연 가능 상태 반영`
- "PR 전체를 대표하는 type을 고른다"는 규칙은 적용하지 않는다.
- 이 제목이 merge commit의 제목이 된다.

### 본문 구성

````markdown
## 릴리스 목적

- 이번 릴리스로 main에 반영되는 상태 (개조식)
  > 지금 올리는 이유 (시연·발표 일정, 마일스톤 등)

## 변경 사항

- develop에 squash된 변경 하나당 불릿 하나
  > 그 변경의 의도

(사용자가 고른 추가 섹션)

Closes #<이슈 번호. 있을 때만>

## 머지 커밋 메시지

```
chore(release): <한국어 제목>

<릴리스 목적 한두 문장>

- <포함된 squash 커밋 제목>

BREAKING CHANGE: <있을 때만>
Closes #<이슈 번호. 있을 때만>
```
````

- `## 릴리스 목적`은 **항상 포함**한다. 불릿은 main에 반영되는 상태를, `>`는 지금 올리는 이유를 쓴다.
- `## 변경 사항`의 불릿 단위는 `origin/main..origin/develop`에 있는 **squash 커밋 하나(= 작업 PR 하나)** 다. 커밋 제목을 개조식으로 옮기고, `>`에는 그 커밋 본문에 있는 의도를 요약해 쓴다. 커밋 본문에 의도가 없으면 지어내지 않고 가이드 질문으로 확인한다.
- 릴리스 목적이 불분명하면 `branch-strategy`의 "의도 확인" 질문을 쓴다 (시연 준비, 최종 발표, 일정 마일스톤 등).
- 추가 섹션은 같은 가이드 질문으로 제안한다. 릴리스에서는 `## 확인 방법`에 시연 가능 여부 확인(핵심 흐름 시나리오 등)을, `## 영향 범위`에 main에 새로 반영되는 범위를 쓴다.
- 이슈 링크: 포함된 커밋 본문의 `Closes #N`을 모아 본문 끝에 나열한다. 작업 PR은 `develop`으로 머지되므로 이슈 자동 종료가 기본 브랜치 반영 시점(릴리스)에 일어난다.
- `## 머지 커밋 메시지`는 **항상 포함**한다. merge commit 본문은 PR 본문과 **별도의 일반 텍스트**이며, 형식과 작성 규칙은 `branch-strategy`의 "Merge commit 메시지"를 따른다 (릴리스 목적 + squash 커밋 제목 목록 + footer, 변경별 의도 제외, 마크다운 서식 없음). 코드 블록에 실어 두어 누가 머지하든 같은 메시지를 복사해 쓰게 한다.

### 절차

1. `git fetch origin`으로 최신 상태를 가져오고, **로컬 `develop`이 아니라 `origin/develop`을 기준**으로 본다. `develop`은 직접 push하지 않으므로 이 절차에서 push는 하지 않는다. 로컬의 커밋되지 않은 변경은 릴리스와 무관하며 `develop`에 커밋하지 않는다.
2. 이미 열린 릴리스 PR이 있는지 확인한다. 있으면 새로 만들지 않고 본문 갱신을 제안한다.

   ```bash
   gh pr list --base main --head develop --state open
   ```

3. 릴리스에 포함될 변경을 파악한다. 비어 있으면 올릴 변경이 없으므로 중단하고 알린다.

   ```bash
   git log --format='%h %s%n%b' origin/main..origin/develop
   git diff origin/main...origin/develop --stat
   ```

4. 릴리스 시점과 목적을 확인한다 (불분명할 때만 가이드 질문). `main`은 시연·발표 가능한 상태만 담는다.
5. 본문을 작성하고 추가 섹션을 가이드 질문으로 제안해 채운다.
6. 완성된 제목과 본문, **머지 커밋 메시지**를 사용자에게 보여주고 확인받는다.
7. 릴리스 PR을 생성한다 (아래 예시는 `## 머지 커밋 메시지` 섹션을 생략한 축약본이다. 전체 구성은 "본문 구성"을 따른다).

   ```bash
   gh pr create --base main --head develop --title "chore(release): P1 신고·접수·세션 흐름 시연 가능 상태 반영" --body "$(cat <<'EOF'

   - 신고 → 접수 → 기술지원 세션 흐름 main 반영
     > 시연 가능한 상태를 main에 고정하기 위함

   ## 변경 사항

   - 저위험 건 분기 규칙 `route()` 추가
     > 표의 값만으로 판정해 고객 안내 건과 기술지원 건을 나누기 위함
   EOF
   )"
   ```

8. PR URL을 전달하고, **merge commit**으로 머지하며 제목과 본문은 PR의 `## 머지 커밋 메시지`를 그대로 쓴다고 안내한다 (PR 본문 전체를 쓰지 않는다). 머지 명령은 `branch-strategy`에 있다.

## 하지 말 것

- 릴리스 PR의 제목에 `chore(release)` 외 type 사용
- 릴리스 PR에서 `## 릴리스 목적`이나 `## 머지 커밋 메시지` 생략
- squash·merge 커밋 본문에 PR 본문 전체(마크다운)를 복사 (릴리스 머지 커밋에는 변경별 의도도 넣지 않는다)
- 작업 PR에서 `## 머지 커밋 메시지` 생략, 또는 그 블록에 `##`·`>` 마크다운 사용
- 의도를 `>`와 머지 커밋 메시지에서 각각 새로 쓰기 (`>`를 줄여 옮긴다)
- 제목을 50자 넘게 쓰기
- 릴리스 PR을 만들면서 로컬 `develop` 기준으로 변경 목록 작성 (`origin/develop` 기준으로 본다)
- 릴리스 PR을 위해 `develop`에 push 또는 커밋
- 릴리스 PR을 squash 또는 rebase로 머지하도록 안내
- 문장형 서술(`~했습니다`, `~하였음`)로 불릿 작성
- `>` 없이 변경 목록만 나열
- `>`에 불릿 내용을 그대로 반복
- 여러 줄 인용에서 일부 줄의 `>` 누락
- 의도를 모르는데 지어내서 채우기 (모르면 질문한다)
