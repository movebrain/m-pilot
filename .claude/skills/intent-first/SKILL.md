# 의도 우선 개발

> 이 저장소(mpilot) 전용 규칙이다. 기능을 구현하기 전에 의도, 계약, 계획을 문서로 먼저 확정한다.

## 적용 범위

기능 단위 작업에 쓴다: 새 기능, 동작 변경, `issues.md`의 US 하나를 구현하는 일.

쓰지 않는다:

- 오타·문구 수정, 문서만 고치는 작업
- 동작이 같은 단순 리팩터(이름 변경, 파일 이동 등)
- 한두 줄로 끝나는 버그 수정 (원인이 분명하고 spec 변경이 없을 때)

경계가 애매하면 `AskUserQuestion`으로 이 스킬을 쓸지 묻는다.

## 1. 루트 문서 먼저 읽기

기능 문서를 쓰기 전에 아래 순서로 읽는다.

1. `docs/intent.md` — **SOT**다. 다른 문서가 이것과 어긋나면 이것이 우선한다. **Ubiquitous Language(용어집)** 절도 읽는다.
2. `docs/spec.md` — 구조, 데이터 모델, 인터페이스, 수용 기준(6.2), 기본값
3. `docs/issues.md`에서 해당 US와 그 완료 조건의 AC 번호
4. 관련 소스(`src/`)가 이미 있으면 그 파일

- 읽고 알 수 있는 것은 묻지 않는다. 문서와 코드에 없는 판단만 묻는다.
- spec에 없는 함수명·필드·흐름을 지어내지 않는다. 이름과 인터페이스는 `spec.md`를 따른다.

## 2. 어떤 기능 문서를 만들까

`docs/{feature-name}/` 아래에 만든다. `{feature-name}`은 **영어 kebab-case**다. 예: `risk-routing`, `self-guide`. 이슈 번호는 이름에 넣지 않고 문서의 근거에 적는다.

먼저 root 문서에 이미 있는 것을 본다.

| 상황 | 만드는 문서 |
| --- | --- |
| `spec.md`·`issues.md`에 해당 US의 **AC와 인터페이스가 이미 있다** | **`plan.md`만**. root 문서를 링크하고 intent·spec은 쓰지 않는다. |
| root에 없는 **새 기능**이거나 동작을 바꾸는 작업 | `intent.md` → `spec.md` → `plan.md` 세 문서 |
| AC는 있는데 인터페이스가 없다(또는 반대) | 없는 쪽만 쓴다. 애매하면 `AskUserQuestion`으로 묻는다. |

```
docs/risk-routing/
├── intent.md   왜, 무엇을 (의도)        ← 새 기능일 때만
├── spec.md     정확히 어떻게 동작해야 하는가 (계약) ← 새 기능일 때만
└── plan.md     어떤 순서로 만드는가 (계획)   ← 항상
```

- 문서는 한국어로 쓴다. 용어는 `intent.md` 용어집 기준으로 쓴다. 예: "에러"로 통일하고 알람·알림·오류는 쓰지 않는다.
- 모든 문서 맨 위에 상태를 둔다: `상태: draft` → `approved` → `done`.

### 문서별 구조 (루트 문서를 축소해 적용)

**intent.md**

- 근거: 관련 US 번호와 루트 문서 링크
- 최우선 의도: 한 문장 인용(`>`)
- 문제: 지금 무엇이 불편한가
- 기대 결과: 끝나면 무엇이 달라지는가
- 제약: 일정, 기술, 안전, 용어 등 루트 문서에서 이어받는 제약과 이 기능만의 제약
- 열린 질문: 아직 정해지지 않은 것, 루트 문서와의 불일치

**spec.md**

- 범위: 하는 것과 하지 않는 것(비범위)
- 인터페이스: 함수·타입·화면의 입출력. 이름은 루트 `spec.md`를 따른다.
- 데이터: 읽고 쓰는 필드, 형식
- 수용 기준(AC): 검증 가능한 문장. 루트 `issues.md`의 AC 번호가 있으면 그 번호를 쓴다.
- 기본값: 팀 확인이 필요한 값은 "(기본값)"으로 표시한다.

**plan.md**

- 근거: 관련 US 번호, 루트 `spec.md`·`issues.md`의 AC 링크(plan만 쓸 때는 여기가 spec 역할을 한다)
- 단계별 작업: 순서와 각 단계의 완료 모습
- 수정할 파일: 새로 만들 파일과 고칠 파일
- 테스트: 어떤 AC를 어떤 테스트가 확인하는가(`unit-test` 스킬)
- 검증: 완료를 선언하기 전에 실행할 것

## 3. 가이드 질문과 승인

**문서마다 가이드 질문으로 완성하고, 승인을 받은 뒤에만 다음 문서로 넘어간다.** 쓰는 문서가 `plan.md` 하나면 승인도 한 번이다.

1. (새 기능일 때) `intent.md`를 쓴다. 승인을 받는다.
2. (새 기능일 때) `spec.md`를 쓴다. 승인을 받는다.
3. `plan.md`를 쓴다. 승인을 받는다.
4. 쓰기로 한 문서가 모두 승인된 뒤에만 구현한다.

각 문서의 절차:

1. 루트 문서와 코드에서 채울 수 있는 부분을 먼저 채운다.
2. 비어 있거나 판단이 필요한 것만 `AskUserQuestion`으로 묻는다. **문서당 1~2회, 회당 최대 4문항**이다.
3. 후보가 있는 질문은 2~3개 선택지로 제시하고, 권장안은 첫 번째에 "(Recommended)"를 붙인다.
4. 답을 반영해 문서를 완성하고, 상태를 `draft`로 두고 사용자에게 검토를 요청한다.
5. 사용자가 승인하면 상태를 `approved`로 바꾸고 다음 문서로 넘어간다.

승인은 사용자의 명시적인 답이다. 침묵이나 질문에 대한 답만으로 승인으로 보지 않는다.

## 4. 루트 문서와 어긋날 때

**루트 문서가 우선이다. 멈추고 질문한다. 루트 문서는 사용자 승인 없이 수정하지 않는다.**

1. 기능 문서 내용이 `docs/intent.md`나 `docs/spec.md`와 어긋나면 작성을 멈춘다.
2. 어긋난 곳(루트 문서의 위치와 기능 문서의 내용)을 사용자에게 보여주고 `AskUserQuestion`으로 묻는다.
3. 기능 문서를 루트에 맞게 고치는 것이 기본이다.
4. 루트 변경이 필요하면 사용자 **승인을 받은 뒤** 루트 문서를 **구현과 분리된 별도 `docs:` 커밋**으로 고친다(`conventional-commit`, `branch-strategy` 스킬).
   - 새 용어는 `intent.md` 용어집에 먼저 추가하고 쓴다.
   - 타입·계약은 소유자가 바꾸고, `spec.md`를 같이 고치며, 의존하는 파트에 알린다(spec 8.2).
5. 승인을 못 받았거나 팀이 정할 일이면 루트는 건드리지 않고 기능 문서의 **열린 질문**에 불일치를 기록한다.

## 5. 구현 중 문서를 바꿔야 할 때

승인된 문서가 틀렸거나 부족하다고 드러나면 **구현을 멈추고** 해당 문서를 고쳐 다시 승인받는다.

- 앞 문서가 바뀌면 뒤 문서(`intent` → `spec` → `plan`)에 영향이 있는지 확인하고, 있으면 함께 고쳐 재승인한다.
- 문서를 고치는 동안 상태는 `draft`로 되돌린다.
- 작은 변경이라는 이유로 문서를 건너뛰고 구현을 계속하지 않는다.

## 6. 구현이 끝난 뒤

- 문서는 지우거나 루트 `spec.md`에 병합하지 않고 **유지**한다.
- 작성한 문서의 상태를 `done`으로 바꾼다.
- 기능 문서는 구현과 **같은 브랜치에서 함께 커밋**한다. 단, 루트 문서 수정은 4번처럼 별도 `docs:` 커밋이다. 브랜치와 PR은 `branch-strategy`, 커밋은 `conventional-commit`, PR은 `create-pr` 스킬을 따른다.

## 하지 말 것

- 필요한 문서 없이, 또는 승인 전에 구현 시작
- 앞 문서의 승인 전에 다음 문서 작성
- 사용자 승인 없이 루트 `docs/intent.md`, `docs/spec.md` 수정
- 루트 문서를 기능 구현 커밋에 섞어 고치기
- 루트 문서와 어긋난 채로 기능 문서를 확정
- root에 AC와 인터페이스가 이미 있는데 intent·spec 문서를 다시 쓰기
- 코드와 문서에서 알 수 있는 것을 사용자에게 묻기
- `spec.md`에 없는 함수명·필드·흐름을 지어내기
- 승인되지 않은 문서 변경 후 구현 계속
- 구현 후 기능 문서를 삭제하거나 상태를 갱신하지 않고 두기
