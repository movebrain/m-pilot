# M-Pilot: 현대무벡스 자동차 도메인 물류 자동화 설비 장애 대응 지원 서비스

> 기획안(무브레인, 2026-10-19 초안)과 대조해 정리한 판이다. 핵심 흐름은 아래 한 문단의 의도를 최우선으로 한다. 기획안과 다른 부분은 문서 끝의 표에 모았고, 본문에는 **(기획안과 다름)** 만 표시했다.
>
> **최우선 의도**: 고객사가 대상 설비와 해당하는 알림(장애)코드를 선택하고 사진(선택)을 올려 신고하면, 엔지니어 대시보드에서 이를 접수하고 저위험 신고 건은 고객사가 직접 조치할 수 있도록 관련 정보를 안내한다. 기술지원이 필요한 건이면 서비스 접수 건별로 세션이 생성되고, AI가 접수된 건을 요약하고 임베딩된 서비스 매뉴얼과 과거 서비스 조치 이력을 바탕으로 엔지니어 질문에 답한다. 이후 엔지니어가 서비스 조치 이력을 작성하면 다음 장애 대응 시 참고할 수 있는 새로운 서비스 접수 건으로 정리된다.

## Problem

현대무벡스 자동차 설비(Mini Loader, SRM, AGV, RTV)에 장애가 나면 기술영업 엔지니어가 대응 근거를 직접 찾아야 한다.

- 장애 시 방대한 매뉴얼에서 해당 알람의 조치를 찾는 데 시간이 든다.
- 과거에 비슷한 장애를 어떻게 해결했는지 활용하기 어렵다. 조치 노하우가 담당자 개인에게 쌓여 있다.
- 신고가 들어온 뒤 원인 파악과 조치 방향 결정까지 걸려 초동 대응이 늦어진다.
- 조치 결과가 다음 대응의 근거로 돌아오지 않는다.
- 초동 지연이 곧 고객사 물류 중단으로 이어진다.

현재 소요 시간의 실측 기준선은 없다. PoC에서는 기준선 없이 진행하고, 시간 단축 효과는 주장하지 않는다. 위 문제들은 팀이 설정한 가정이며 기업 확인이 필요하다.

## Proposed outcome

### 핵심 흐름

1. **신고**: 고객이 클라이언트 인터페이스에서 설비와 알림(장애)코드를 선택하고, 증상 메모(선택)와 사진(선택)을 올린다. 제출하면 접수번호가 자동으로 부여되고 접수 버튼은 없다. 사진은 AI가 판독하지 않고 엔지니어가 눈으로 확인한다. 고객은 접수 상태(접수 / 분석 중 / 조치 중 / 완료)와 조치 결과를 볼 수 있다. **(기획안과 다름: 증상은 선택 입력)**
2. **접수·분기**: 엔지니어 대시보드가 신고를 접수하고, 시스템 규칙이 즉시 분기한다. **(기획안과 다름: 기획안에 없는 분기)**
   - **저위험 건**: 고객에게 조치 안내를 보낸다. 세션은 만들지 않고, 대시보드 목록에는 "고객 안내"로 표시한다. 고객이 "해결됨"을 누르면 완료되고, "해결 안 됨"을 누르면 기술지원 건으로 전환된다.
   - **그 밖의 건(기술지원 필요)**: 다음 단계로 간다.
3. **기술지원 세션**: 기술지원 건에만 접수 건별 세션이 생성된다. 엔지니어가 세션을 열면 AI가 접수 건을 요약하고 대응 방안까지 자동으로 보여준다. 이후 엔지니어 질문에 임베딩된 서비스 매뉴얼과 과거 서비스 조치 이력을 근거로 출처와 함께 답하고, 후속 질문을 이어갈 수 있다(대화 기억). **(기획안과 다름: 사전 브리핑 대신 요약과 대응 방안, 세션은 기술지원 건만)**
   - 에러코드는 정확 조회, 증상은 의미 검색으로 나눈다. 장비를 기준으로 걸러서 다른 장비의 같은 코드나 비슷한 코드를 혼동하지 않는다.
   - 근거를 찾지 못하면 추측하지 않고 "근거 부족"으로 표시하고 담당 엔지니어 확인을 안내한다(에스컬레이션).
4. **조치 이력 작성과 환류**: 엔지니어가 현장 조치 후 이력을 작성하면 세션 조회 기록으로 초안이 자동으로 채워진다. 엔지니어가 자유서술로 보완하고 AI가 구조화(원인, 조치, 결과 등)하며, 답변이 "예상과 달랐는지"를 체크박스 하나로 표시한다. 엔지니어가 확인해 저장하면 신고, 요약, 제안과 근거, 조치가 **접수 건 한 레코드**로 정리되어 다음 장애 대응의 근거가 된다. 확정된 이력만 검색한다. **(기획안과 다름: 이력의 단위가 접수 건)**

고객·엔지니어의 조치 완료 확인과 서명은 앱 밖에서 하고, 앱에는 구현하지 않는다(시나리오로만).

### 우선순위 **(기획안과 다름)**

기획안은 P1이 접수 없이 장비·코드·증상을 직접 묻는 현장 조회 Q&A 화면이었다. 이 문서는 접수 건 흐름을 중심으로 다시 잡는다. P2는 P1이 끝난 뒤에 착수한다.

| 우선순위 | 범위                                                                                                               |
| -------- | ------------------------------------------------------------------------------------------------------------------ |
| P1       | 신고 → 접수·분기 → 기술지원 세션(요약, 대응 방안, 질문 답변). P1에서는 분기가 "모든 신고를 기술지원 건으로" 보낸다 |
| P2       | 조치 이력 작성과 환류, 저위험 건 분기와 셀프 가이드, 정답률 평가 실행                                              |
| P3(선택) | 접수 없이 묻는 독립 조회 Q&A 화면, 평가 화면, 설비 추가(표 추가 후 재인덱싱)                                       |

### 셀프 가이드

저위험 건의 기준은 에러코드 표로 정한다. 표에 `등급`(A/B/C/I)과 `가이드 문구` 컬럼을 두고, 작성자가 고객이 직접 해도 되는 코드에만 문구를 쓴다. 등급이 C/I이면서 가이드 문구가 비어 있지 않은 코드만 저위험 건이다. 등급 A/B는 문구가 있어도 항상 기술지원 건이다. 분기는 에러코드만 보고 정하며 증상 메모와 사진은 쓰지 않는다. 판정 모델, 승인 화면, 별도 조치 주체 컬럼은 만들지 않는 규칙 단순형이다. **(기획안과 다름: 기획안에 없는 기능)**

### 성공 판단: 정답률

평가 질문 30~40문항(데이터를 쓰지 않은 사람이 작성)으로 다음을 잰다. 평가는 화면 없이 엔진을 직접 호출해 돌린다.

- 에러코드 정확 조회 정답률과 장비 혼동 여부
- 증상 검색에서 올바른 매뉴얼·이력이 상위 결과에 있는지
- 데이터에 없는 질문에 지어내지 않는 비율("근거 부족" 처리)
- 응답 시간

정답 판정에서는 인용된 출처가 실제 근거인지도 함께 본다. 평가는 고정된 데이터 스냅샷으로 하고, 이력 추가 전/후 비교는 별도 시연으로 보여준다. 목표치는 두지 않고 측정을 우선한다.

### 시연용 보조 지표: 제안 채택률 **(기획안과 다름)**

조치 기록 시 "예상과 달랐는지"에 체크하지 않은 비율을 수치 한 줄로 슬라이드에 넣는다. 가상 데이터라 의미가 약해서 대표 지표로 쓰지 않는다.

## Affected users and systems

- 사용자: 현대무벡스 서비스 엔지니어(주 사용자: 대시보드, 세션 Q&A, 조치 이력 작성), 고객사 담당자(보조 사용자: 신고, 상태 확인, 셀프 가이드)
- 시스템(신규): 고객 신고 화면, 엔지니어 대시보드(접수 목록, 기술지원 세션 Q&A 포함), 검색 엔진(질문 분석, 에러코드 정확 조회, 매뉴얼·이력 의미 검색), 답변 생성(요약, 대응 방안, 질문 답변), 접수 건 저장소(이력 포함), 설비 레지스트리. 화면은 Gradio의 Tab으로 구분한다.
- 자료(전부 가상):
  - 설비 4종(Mini Loader, SRM, AGV, RTV)별 에러코드 표를 팀이 만든다. 설비당 8~10개이고, 표를 원본으로 두고 검색용 문서는 표에서 생성해 두 곳의 내용이 어긋나지 않게 한다. 사양서의 산문 본문(설비 개요, 구성)은 두지 않는다.
  - 에러코드 표의 공통 코어 컬럼은 설비, 코드, 등급(A/B/C/I), 증상, 원인, 조치, 가이드 문구다. 설비별 부가 정보는 확장 필드(JSON)로 둔다. 등급과 가이드 문구 컬럼은 **(기획안과 다름)**
  - 접수 건 한 레코드는 신고(설비, 코드, 증상 메모, 사진 유무), 상태, 분기 결과, AI 요약, 제안과 근거, 엔지니어 조치, 결과, "예상과 달랐는지" 체크박스, `source`(작성 / 엔지니어 입력)로 이루어진다.
  - 가상 서비스 조치 이력 50건을 팀이 접수 건 형식으로 만든다. 가상 이력의 AI 요약·제안·근거 필드는 비워 둘 수 있다(spec에서 확정). **(기획안과 다름: 기획안은 100건 안팎, 복합 장애 5~10건 포함. 이 문서는 50건이고 복합 장애는 뺀다)** 일부러 넣을 함정은 다른 장비의 같은 코드, 같은 장비 안의 비슷한 코드, 매뉴얼과 다른 실제 조치, 표기가 제각각인 이력이다. 신고에서 코드를 반드시 고르므로 코드 없는 이력은 만들지 않는다. **(기획안과 다름)**
  - 평가 질문 세트 30~40문항, 장비 목록, 용어·동의어 사전을 만든다. 평가 질문은 데이터를 쓰지 않은 사람이 쓴다.
  - 제품 카탈로그(E-Cat2025)는 실제 공개 문서이고, 공개 저장소에 올리지 않는다.
  - 모든 화면에 "모든 데이터는 가상"이라는 안내를 띄운다.
  - 팀 내 데이터 담당 2명이 서로의 자료를 검수한다. 등급 A/B 기재와 가이드 문구(안전 수칙에 어긋나지 않는지)는 반드시 확인한다. 기획안은 설비 경험자의 검수가 필요하다고 보지만, 이 문서는 팀 내 상호 검수로 정했다. **(기획안과 다름)**
  - 사진은 저장하고 엔지니어가 열람한다. 이미지 내용 해석은 하지 않는다. 로그 파일 첨부는 없다.

## Constraints

- **범위와 일정**: 사내 PoC/시연용이다. 실도입은 범위 밖이다. 본 프로젝트 일정은 2026-10-21~11-02이고 문서는 기획안의 8 Day(Day 1~8)를 기준으로 설계한다. 최종 발표는 11-02다. 10/23(금) 등 추가 작업일이 생기면 통합·정확도 반복의 완충으로 쓴다. spec.md는 Day 1 전(10/19~20)에 쓴다. 팀은 7명이고 역할은 기획안의 7역할(PM·발표 / 데이터 2명 / 검색·RAG / 답변·프롬프트 / UI / 테스트·평가)을 따른다.
- **기술**: Python, OpenAI(또는 Gemini) API, LangChain, Gradio, pandas, 수업에서 쓰는 벡터DB. 새 기술은 테스트에서 실제 문제가 드러날 때만, 이유를 설명할 수 있을 때 추가한다.
- **고객사 식별자**: PoC는 단일 고객사로 구현한다. 접수 건 레코드에만 `customer_id` 상수 컬럼을 두어, 결과가 좋을 때 다중 고객사로 넓힐 여지를 남긴다. 이 필드의 검증 항목, 격리 필터, 권한은 만들지 않는다. 로그인과 권한은 시나리오로만 두고, 고객/엔지니어는 Tab으로 구분한다. **(기획안과 다름: 기획안에 없는 필드)**
- **클라우드 LLM API**: 모든 자료가 가상이므로 마스킹하지 않는다.
- **안전**: 등급 A/B 코드는 가이드 문구가 있어도 고객에게 안내하지 않는다. 문구 작성 실수로 위험 코드가 열리지 않게 등급 값만으로 막는 규칙이다. 등급 C/I 코드 중 작성자가 가이드 문구를 쓴 코드만 저위험 건이며, 비어 있으면 기술지원 건이다. 매뉴얼의 공통 안전 수칙(LOTO, 캐리지 고정, 안전 파라미터 변경 금지)과 상충하는 안내는 하지 않는다.
- **신뢰성**: 모든 요약, 대응 방안, 답변에 출처를 인용하고, 근거가 없으면 "근거 부족" 표시와 에스컬레이션으로 처리한다. 기획안의 "확인 불가"와 같은 개념이며 용어는 "근거 부족"으로 통일한다. **(기획안과 다름: 용어)**
- **이력 품질**: 조치 기록은 엔지니어 확인 후 저장하고, 확정된 이력만 검색한다. 진행 중인 접수 건은 이력으로 검색하지 않는다. 이력 오염을 막기 위한 규칙이다.
- **표현**: "AI가 학습한다"가 아니라 "검색 근거가 늘어난다"로 설명한다.
- **언어**: 한국어만 지원한다.

## Open questions

1. 기획안과 달라지는 항목을 팀과 강사님에게 확인해 확정해야 한다. 특히 P1 범위가 커졌다. 기획안의 P1은 화면 하나(조회 Q&A)였고, 이 문서의 P1은 고객 신고, 대시보드, 세션 Q&A와 분기를 포함한다. Day 5 "P1 완성"이 빡빡하고 UI 담당 과부하도 커지므로 일정과 함께 합의가 필요하다.
2. 평가 질문 세트를 누가 쓰나? "데이터를 쓰지 않은 사람" 조건을 7역할의 테스트·평가 담당이 충족하는지 확인해야 한다.
3. 기획안이 강사님께 확인하려던 사항(프로젝트 요구사항 문서와 온보딩 가이드 중 기준 문서, 사용자 둘 구성의 범위 적합성)은 아직 열려 있다.
4. spec에서 확정할 항목:
   - "근거 부족" 판정 기준. 세션 생성 시 자동으로 나오는 요약과 대응 방안에도 적용한다(검색 점수 임계값을 평가 질문으로 조정).
   - 인용이 실제 근거인지 확인하는 방식(사람이 샘플 확인).
   - 벡터DB 공유와 스냅샷 복원 절차(생성 스크립트를 저장소에 두고 각자 재생성).
   - 고객 Tab 노출 통제 수준(Gradio Tab만으로는 접근을 막을 수 없으므로 "표시하지 않는다" 수준으로 낮출지).
   - 1000자 분할과 코드 단위 청킹의 비교를 할지(선택).
   - 증상 메모와 선택한 코드가 어긋날 때의 처리(요약에 둘 다 보여주고 코드를 우선).
   - 가상 이력의 AI 요약·제안·근거 필드를 비워 둘지.
   - 상태 값. 기본값은 4단계(접수 / 분석 중 / 조치 중 / 완료)이고, 저위험 건은 "접수"에 "고객 안내" 표시가 붙는다. 엔지니어가 세션을 열면 "분석 중"이 된다.
   - 저위험 건에서 고객이 "해결됨"을 누르면 엔지니어 확인 없이 곧바로 "완료"로 한다(기본값).

## 기획안과 다른 점

| 항목             | 기획안                                            | 이 문서                                                              | 팀 확인          |
| ---------------- | ------------------------------------------------- | -------------------------------------------------------------------- | ---------------- |
| P1 범위          | 독립 현장 조회 Q&A 화면. 접수·대시보드는 P2       | 신고 → 분기 → 세션 Q&A가 P1. 독립 조회 화면은 P3                     | 필요 (일정 영향) |
| 접수 후 분기     | 없음                                              | 시스템 규칙이 접수 즉시 분기. 저위험은 고객 안내, 그 밖에는 기술지원 | 필요 (일정 영향) |
| 셀프 가이드      | 없음                                              | 분기의 저위험 안내(P2). 에러코드 표의 등급·가이드 문구 컬럼          | 필요             |
| 세션             | 접수번호 단위로 후속 질문                         | 기술지원 건에만 접수 건별 세션 생성                                  | 필요             |
| 사전 브리핑      | P2에 포함                                         | 제외. 세션 시작 시 AI 요약과 대응 방안 자동                          | 필요             |
| 신고 입력        | 장비, 에러코드, 증상, 사진                        | 설비·코드 선택(필수), 증상 메모(선택), 사진(선택)                    | 확인             |
| 이력 단위        | 서비스 이력 레코드                                | 접수 건 한 레코드(신고, 요약, 제안과 근거, 조치)                     | 확인             |
| 이력 규모·함정   | 100건 안팎, 복합 장애 5~10건, 코드 없는 이력 포함 | 50건, 복합 장애·코드 없는 이력 제외                                  | 필요             |
| 이력 검색        | 의미 검색                                         | 확정된 이력만, 실패 이력 표시 추가                                   | 확인             |
| 지표             | 정답률 중심                                       | 정답률 + 시연용 채택률 수치 한 줄                                    | 확인             |
| 상태             | 접수 상태 확인(단계 미정)                         | 4단계 + 저위험 "고객 안내" 표시                                      | 확인             |
| `customer_id`    | 없음                                              | 접수 건에 상수 컬럼                                                  | 확인             |
| 용어             | 무브레인, "확인 불가"                             | M-Pilot, "근거 부족"                                                 | 확인             |
