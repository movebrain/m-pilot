# M-Pilot: 현대무벡스 자동차 도메인 물류 자동화 설비 장애 대응 지원 서비스

> **최우선 의도**: 서비스 엔지니어가 서비스 매뉴얼과 과거 서비스 조치 이력에서 장애 대응의 근거를 바로 찾고, 그 서비스 조치 결과가 다음 대응의 근거로 쌓이게 한다.
>
> 이 문서가 기준 문서(SOT)다. spec.md 등 하위 문서는 이 문서와 어긋나지 않는다. 이 문서는 "왜, 무엇을"만 다루고, 수치 기준·구조·인터페이스는 spec.md가 정한다.

## Problem

현대무벡스 자동차 설비(Mini Loader, SRM, AGV, RTV)에 장애가 나면 서비스 엔지니어가 대응 근거를 직접 찾아야 한다.

- 방대한 매뉴얼에서 해당 에러의 조치를 찾는 데 시간이 든다.
- 과거에 비슷한 장애를 어떻게 해결했는지 활용하기 어렵다. 조치 노하우가 담당자 개인에게 쌓여 있다.
- 조치 결과가 다음 대응의 근거로 돌아오지 않는다.

위 문제들은 팀이 설정한 가정이며 기업 확인이 필요하다. 소요 시간의 실측 기준선이 없으므로 시간 단축 효과는 주장하지 않는다.

## Ubiquitous Language

> 이 절의 용어가 프로젝트의 공용어다. 화면 문구, spec.md, 코드, 평가 질문, 팀 대화에서 같은 말을 쓴다. "쓰지 않는 말"은 다른 뜻과 섞이거나 사양서 용어와 어긋나서 피하는 표현이다. 영어 식별자는 spec.md 5·6장과 python-naming 스킬 규칙을 따르고, 새 용어는 이 표에 먼저 추가한다.

| 상태 | 고객에게 보이는 접수 건의 진행 단계. 접수 / 분석 중 / 조치 중 / 완료. | |

### 서비스 조치 이력과 서비스 이력 추가

| 용어 | 정의 | 쓰지 않는 말 |
| --- | --- | --- |
| 서비스 조치 | 현장에서 한 조치(행위). 엔지니어가 한 조치가 중심이고, 가상 이력에는 고객사가 직접 한 조치도 있다. 누가 했는지는 조치자로 구분한다. 그 기록은 서비스 조치 이력이다. | 조치(단독) |
| 서비스 조치 이력 | 엔지니어가 작성하는 서비스 조치의 기록. 원인·서비스 조치·결과 3개 필드로 구조화한다. | 로그 |
| 결과 | 서비스 조치 결과. `해결` / `미해결`. 해결일 때만 상태가 완료가 된다. 임시 조치(재발 감시)는 `미해결`로 본다. | |
| 조치자 | 조치를 한 주체(서비스 엔지니어, 고객사 운영자, 자동 복구 등). | |
| 예상과 달랐는지 | 대응 방안이 현장 결과와 달랐는지 표시하는 체크박스 하나. | |
| 확정 | 엔지니어가 확인해 저장하는 일. 확정된 접수 건만 이력이 된다. | 승인 |
| 이력 | 확정되어 검색 대상이 된 접수 건(과거 사례). 제공된 장애 기록을 접수 건 형식으로 바꾼 것과 팀이 보강한 건이 가상 이력이다. 고객사가 직접 조치한 기록도 포함한다. 결과가 `미해결`인 이력은 검색에서 제외하지 않고 "실패 이력"으로 표시한다. | 로그 |
| 서비스 이력 추가 | 확정한 접수 건이 이력에 추가되어 다음 대응의 근거가 되는 흐름. 기존 이력을 고치지 않고 새 접수 건을 더한다. "검색 근거가 늘어난다"로 설명한다. | 환류, 업데이트(수정으로 읽힘), 학습, 재학습 |

## Proposed outcome

### 핵심 흐름

1. **신고**: 고객이 설비와 에러코드를 고르고 증상 메모와 사진(모두 선택)을 올린다. 한 건에 여러 쌍을 보낼 수 있다(복합 장애). 제출하면 건 단위로 접수번호가 부여된다. 고객은 상태와 서비스 조치 결과를 볼 수 있다.
2. **접수·분기**: 신고가 제출되면 시스템이 즉시 접수 건으로 만들고 규칙으로 분기한다. 엔지니어 대시보드는 접수된 건을 본다.
   - **저위험 건**: 셀프 가이드를 보낸다(사양서 표 9-4의 `조치` 열 그대로). 세션은 만들지 않는다. 고객이 "해결됨"을 누르면 완료, "해결 안 됨"을 누르면 기술지원 건으로 전환된다.
   - **기술지원 건**: 심각도가 상이면 조치 구분과 무관하게 항상 기술지원 건이고, 사양서가 고객사 조치로 분류한 코드라도 고객에게 안내하지 않는다.
   - **복합 신고**: 쌍 중 하나라도 저위험이 아니면 건 전체가 기술지원 건이고 저위험 쌍의 셀프 가이드도 보내지 않는다.
   - 분기는 에러코드 표의 값(조치 구분, 심각도)만으로 정한다. 위험 코드는 문구가 아니라 심각도 값으로만 막고, 증상 메모와 사진은 쓰지 않는다. 판정 기준과 수치는 spec.md 4장과 AC-11이 정한다.
3. **기술지원 세션**: 기술지원 건에만 세션이 생긴다. 엔지니어가 세션을 열면 AI가 요약과 대응 방안을 보여주고, 이후 질문에 서비스 매뉴얼과 이력을 근거로 출처와 함께 답한다. 후속 질문을 이어갈 수 있다.
   - 에러코드는 키워드 기반 조회, 증상은 의미 검색으로 나누고 설비로 걸러서, 다른 설비의 비슷한 에러(예: 주행 브레이크 이상 R206 / S115 / M406)를 혼동하지 않는다.
   - 복합 신고는 세션 하나에서 쌍별로 근거를 구분해 보여준다. 쌍 사이의 인과 관계는 근거가 있을 때만 말한다.
   - 근거를 찾지 못하면 추측하지 않고 "근거 부족", 4개 설비 밖 질문은 "적용 대상 아님"으로 표시한다.
4. **서비스 조치 이력 작성과 서비스 이력 추가**: 엔지니어가 서비스 조치 후 서비스 조치 이력을 작성하면 세션 기록으로 초안이 채워진다. 엔지니어가 보완하면 AI가 원인·조치·결과로 구조화하고, 답변이 "예상과 달랐는지"를 표시한다. 엔지니어가 확인해 저장하면 접수 건 한 레코드로 정리되어 다음 대응의 근거가 된다.

| 우선순위 | 범위 |
| -------- | ---- |
| P1 | 신고 → 접수·분기 → 기술지원 세션(요약, 대응 방안, 질문 답변). P1의 분기는 모든 신고를 기술지원 건으로 보낸다. 에러코드 표와 사양서 본문 파싱·임베딩 포함 |
| P2 | 서비스 조치 이력 작성과 서비스 이력 추가, 저위험 분기와 셀프 가이드, 정답률 평가 실행 |
| P3(선택) | 접수 없이 묻는 독립 조회 Q&A 화면, 평가 화면, 설비 추가 |

P2는 가짜 구현 위에서 P1과 병행 개발하되, 실제 통합과 시연은 P1 통합이 끝난 뒤에 한다.

### 성공 판단: 정답률

평가 질문(데이터를 쓰지 않은 사람이 작성)을 화면 없이 엔진을 직접 호출해 고정된 데이터 스냅샷에서 돌린다. 목표치는 두지 않고 측정하며, 지표의 정의와 계산은 spec.md 8장이 정한다. 정답 판정에서는 인용된 출처가 실제 근거인지도 본다. 이력 추가 전/후 비교는 별도 시연이고, 대응 방안 채택률은 가상 데이터라 시연용 보조 지표로만 쓴다.

## Affected users and systems

- **사용자**: 현대무벡스 서비스 엔지니어(주 사용자: 대시보드, 세션 Q&A, 서비스 조치 이력 작성), 고객사 담당자(이하 고객. 보조 사용자: 신고, 상태 확인, 셀프 가이드)

## Constraints

- **범위와 일정**: 사내 PoC/시연용이며 실도입은 범위 밖이다. 일정은 2026-10-21~11-02, 최종 발표는 11-02다. 추가 작업일은 통합·정확도 반복의 완충으로 쓴다.
- **기술**: Python, OpenAI(또는 Gemini) API, LangChain, Gradio, pandas, pdfplumber, MySQL(실행 방식은 spec.md가 정한다), 수업에서 쓰는 벡터DB. 새 기술은 테스트에서 실제 문제가 드러나고 이유를 설명할 수 있을 때만 추가한다.
- **설비 단위**: 설비별 세부 모델(예: RTV-S10, SRM-P)은 특정하지 않는다. 사양서에 모델별 정보가 있어도 설비 4종 단위로만 다루고, 모델별 값은 답변에 병기한다.
- **고객사**: 단일 고객사로 구현하고 다중 고객사로 넓힐 여지(고객사 식별자)만 남긴다. 로그인·권한은 시나리오로만 두고 고객/엔지니어는 Tab으로 구분한다.
- **범위 밖**: 사진은 저장해 엔지니어가 눈으로 확인할 뿐 AI가 판독하지 않는다. 로그 파일 첨부는 없다. 조치 완료 확인과 서명은 앱 밖에서 한다(시나리오로만).
- **자료**: 모든 자료는 가상이다. 클라우드 LLM API에 보내도 마스킹하지 않는다. 제품 카탈로그(E-Cat2025)는 실제 공개 문서이므로 공개 저장소에 올리지 않는다.
- **안전**: 기술지원 건의 기술지원 대기 안내는 사양서 원칙(안전 확보, 설비 정지 유지, 기술지원팀 연락)을 따르고, 매뉴얼의 공통 안전 수칙(LOTO, 캐리지 고정, 안전 파라미터 변경 금지)과 상충하는 안내는 하지 않는다.
- **신뢰성**: 모든 요약, 대응 방안, 답변에 출처를 인용하고 "근거 부족"·"적용 대상 아님" 규칙(핵심 흐름 3)을 적용한다.
- **데이터 검수**: 저위험 코드의 조치 문구가 안전 수칙에 어긋나지 않는지, 다른 절 참조("11.1절 참조" 등)나 전문 용어가 고객에게 그대로 나가도 되는지는 사람이 반드시 확인한다. 검수 담당은 roles.md가 정한다.
- **표현·언어**: 한국어만 지원한다. 모든 화면에 "모든 데이터는 가상" 안내를 띄운다. 용어와 금지 표현은 Ubiquitous Language를 따른다.

## Open questions

1. P1 범위(고객 신고, 대시보드, 세션 Q&A, 분기, 사양서 파싱·임베딩)가 커서 일정이 빡빡하다. 팀과 강사님의 합의가 필요하다.
2. 평가 질문 작성자가 "데이터를 쓰지 않은 사람" 조건을 충족하는지 확인한다.
3. 사용자 둘(엔지니어, 고객사 담당자) 구성이 프로젝트 범위에 적합한지 강사님께 확인한다.

구현 수준의 결정(상태 전이, "근거 부족" 임계값, 인용 확인 방식, 청킹, 스냅샷 복원 등)은 spec.md의 기본값으로 둔다.
