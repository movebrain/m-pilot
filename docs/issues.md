# 이슈 초안 (사용자 스토리 단위)

- 형식: 저장소 이슈 템플릿(기능 추가 | 개선). 제목은 `⚙️ [기능추가][카테고리][담당 파트] US-번호 제목`, 라벨은 `작업 전`이다. 카테고리는 템플릿의 전처리 / DB / 데이터 / RAG / LLM / UI / 평가 / 통합 중에서 골랐다.
- 단위: 사용자 스토리(US) 24개이고, 이슈 하나가 스토리 하나다. 스토리 하나는 담당 파트 한 곳이 책임진다. 근거는 기능 명세 7장이고, 완료 조건 끝의 번호(예: AC-06.1)가 그 인수 기준이다.
- 스토리 번호는 담당 파트 순서, 파트 안에서는 우선순위 순서로 매겼다.
- 파일·경로·함수 이름은 베이스라인과 환경처럼 꼭 필요한 곳에만 쓰고, 구체적인 이름은 기능 명세의 인터페이스를 따른다.
- 담당자는 비워 두었다. 이슈를 올릴 때 `@`로 지정한다. 브랜치는 기여 가이드대로 개발 브랜치에서 기능 브랜치를 만들어 작업한다.
- 다른 파트의 결과가 오기 전에는 베이스라인의 스텁(모의 데이터를 돌려주는 시그니처)과 개발용 샘플 위에서 먼저 개발하고, 담당이 자기 모듈의 스텁을 실제 구현으로 덮어쓰고, 자기 AC 테스트와 계약 테스트를 통과한 PR로만 develop에 머지한다. 베이스라인(전 모듈의 스텁, `tests/conftest.py`)은 스토리가 아니라 기능 명세의 설계 규칙이고 서비스 이력 담당이 먼저 올린다. DB는 MySQL 담당의 첫 버전 `db`를 쓴다.

# 벡터 DB·데이터

### ⚙️ [기능추가][전처리][벡터 DB·데이터] US-01 사양서 기준의 에러코드 표와 본문 준비

**우선순위**: P1

#### 📝 배경

- 엔지니어는 설비와 코드마다 정확한 원인·조치를 믿고 보려고, 사양서 기준으로 정리된 에러코드 표와 사양서 본문을 원한다.

#### 🎯 목표

- 다른 파트가 검증된 에러코드 표와 본문 조각을 바로 가져다 쓸 수 있다.

#### ✅ 완료 조건 (작업 목록)

- [ ] 에러코드 표가 249행이고 심각도·조치 구분이 빈 행이 없다. (설비, 코드)가 중복이면 불러오기가 실패하고, 동명 에러는 설비와 코드로 구분해 조회된다 (AC-01.1)
- [ ] 사양서 표 9-4와 에러코드 CSV를 코드 기준으로 합치고, 심각도·조치 구분이 어긋난 행을 목록으로 보고한다 (AC-01.2)
- [ ] 에러코드 표의 설비는 4개뿐이고, 이것이 설비 목록이 된다 (AC-01.2)
- [ ] 사양서 본문이 쪽·절 정보가 붙은 조각으로 나뉜다 (AC-01.3)
- [ ] 사양서 4종이 접두 체계(R/S/A/M) 개정본이고 코드 집합이 에러코드 CSV와 일치하는지 확인했다. 표 9-4의 `대상 모델`이 `전 모델`이 아닌 행은 부가 정보에 보관한다
- [ ] 저위험 78개 문구를 MySQL 담당이 안전 수칙 부합 여부로 검수했다

# 벡터 DB·인덱싱

### ⚙️ [기능추가][DB][벡터 DB·인덱싱] US-02 인덱스 재생성과 설비 필터 검색·인용 원문 조회

**우선순위**: P1

#### 📝 배경

- 팀원(검색 파트)은 인덱스를 기다리지 않고 개발하려고, 원본에서 인덱스를 다시 만들고 설비 필터가 걸린 검색과 인용 원문 조회를 쓰길 원한다.

#### 🎯 목표

- 원본에서 인덱스를 언제든 다시 만들 수 있고, 설비 필터가 걸린 검색과 인용 원문 조회가 된다.

#### ✅ 완료 조건 (작업 목록)

- [ ] 베이스라인의 `indexing` 스텁을 실제 구현으로 덮어쓰고 시그니처와 타입은 그대로다
- [ ] 원본(에러코드 표, 사양서, 이력 시드)을 고치고 인덱스를 다시 만들면 검색 문서가 따라 바뀐다. 표 문서 1개 = 에러코드 1행이다 (AC-02.1)
- [ ] 설비 필터를 적용한 검색이 거리와 메타데이터가 붙은 결과를 돌려주고, 다른 설비의 문서가 나오지 않는다 (AC-02.2)
- [ ] 출처 식별자로 인용 원문(표 행, 본문, 이력)을 가져올 수 있다 (AC-02.2)
- [ ] 실제 구현은 불러올 때 벡터 DB에 접속하지 않는다
- [ ] 평가 직전에 인덱스를 시드 상태로 되돌릴 수 있다

#### 🎯 목표

- [ ] 복합 건은 쌍마다 문서로 추가되고, 이력 검색 결과는 같은 접수 건이 한 번만 나오도록 중복이 제거된다 (AC-03.1)

# MySQL

### ⚙️ [기능추가][DB][MySQL] US-04 접수 건과 대화 기록 저장

**우선순위**: P1

#### 📝 배경

- 엔지니어는 접수 건과 대화 기록이 저장되어 세션을 다시 열어도 이어지길 원한다. 고객 접수, 엔지니어 세션, 서비스 이력 파트가 모두 이 저장소를 쓴다.

#### 🎯 목표

- 접수 건의 생성·조회·수정, 대화 기록, 상태 전이를 안정적으로 제공한다.

#### ✅ 완료 조건 (작업 목록)

- [ ] 접수 건을 만들면 접수번호(SC-날짜-순번)가 부여되고 설비-에러코드 쌍 1~4개가 함께 저장되며(0개, 5개 이상, 같은 쌍 중복은 거부. 같은 설비의 다른 코드는 허용) 상태가 접수로 저장된다. 동시에 접수해도 접수번호가 겹치지 않는다 (AC-04.1)
- [ ] 요약·대응 방안·대화 기록·상태를 저장하고 조회한다. 상태 전이는 정해진 표대로만 허용되고, 허용되지 않는 전이는 에러가 난다 (AC-04.2)
- [ ] 다른 파트가 쓸 MySQL 환경(`docker-compose.yml`)과 `db` 첫 버전을 가장 먼저 제공한다. 로컬 DB 테스트는 연결을 목으로 바꿔 DB 없이 통과하고, SQL 동작 테스트는 CI의 MySQL(시연용과 분리된 테스트 DB)에서만 통과한다
- [ ] 사진 경로를 저장하고, 증상 메모·사진은 비어 있어도 접수된다

- [ ] 적재 후 건수가 일치하고, 적재한 이력은 팀 작성·확정 상태다 (AC-05.2)
- [ ] 변환 규칙(결과 대응, 적재하지 않는 열)을 정했고 변환 스크립트로 다시 만들 수 있다

# 고객 접수

### ⚙️ [기능추가][UI][고객 접수] US-06 설비·에러코드를 골라 신고하고 접수번호 받기

**우선순위**: P1

#### 📝 배경

- 고객은 설비와 에러코드를 골라 신고하고 초동 대응을 빨리 받길 원한다. 사진과 증상 메모는 선택이다.

#### 🎯 목표

- 고객이 신고를 제출하면 접수번호를 받고 접수 건이 생성된다.

#### ✅ 완료 조건 (작업 목록)

- [ ] 설비와 에러코드는 필수이고, 에러코드는 고른 설비의 목록에서만 고른다. 한 건에 쌍을 1~4개 고를 수 있고 같은 쌍을 두 번 고르거나 5번째 쌍을 추가할 수 없다. 같은 설비의 다른 코드는 함께 고를 수 있다. 증상 메모와 사진은 비워도 접수된다 (AC-06.1)
- [ ] 사진은 jpg/jpeg/png, 5MB 이하만 저장한다. 초과하면 거부 메시지를 보이되 사진 없이 접수할 수 있다 (AC-06.2)
- [ ] 제출하면 접수번호가 보이고 별도의 접수 버튼은 없다. 처리 순서는 접수 생성 → 분기 → 접수 갱신이다 (AC-06.3)
- [ ] 다른 파트가 아직 없을 때를 위해 `db` 첫 버전과 스텁 위에서 먼저 끝까지 동작한다

- 팀원은 시연 전에 품질을 숫자로 보이려고, 평가 질문으로 정답률 등 지표를 재고 통합 시나리오로 전체 흐름을 점검하길 원한다. 별도 평가 인원이 없어 서비스 이력 담당이 겸한다.

#### 🎯 목표

- 고정된 상태에서 같은 결과를 내는 평가와, 통합 시나리오를 모두 통과하는 점검이 있다.

#### ✅ 완료 조건 (작업 목록)

- [ ] 평가 질문 30~40문항이 있다(조회, 증상, 설비 혼동, 복합 신고, 근거 없음, 적용 대상 아님, 사양서 본문). 에러코드·이력 데이터를 만들지 않은 사람이 쓰고, 정답 출처는 벡터 DB·데이터와 MySQL 담당이 확인했다
- [ ] 화면 없이 엔진을 직접 호출해 평가하고, 지표를 유형별로 계산한다(복합 신고 3~5문항의 쌍별 근거 지표 포함). 채택률은 정답률과 독립적으로 돈다 (AC-17.1)
- [ ] 고정된 스냅샷에서 두 번 실행해 결과가 같다 (AC-17.1)
- [ ] 인용 정확도는 사람이 무작위 20개 단계를 확인한다
- [ ] 통합 시나리오 1~4를 통과한다: 1 저위험 신고 → 셀프 가이드 → 해결됨 → 완료, 2 심각도 상 신고 → 세션 → 인용 확인 → 이력 확정, 3 재신고 시 방금 확정한 이력이 근거로 나타남, 4 복합 신고 시 건 전체가 기술지원이고 쌍별 근거가 구분됨 (AC-17.2)
- [ ] 각 파트가 자기 스토리의 계약 테스트를 쓰도록 형식을 합의했다
